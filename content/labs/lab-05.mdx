<Step n={2} title="Understand facts and rules" time="5 min" id="look">

Open `inference.py` and read the comment at the top. Two ideas carry the whole lab.

A **fact** is simply a string that names something known to be true, such as `"passed_math1"`. A set of facts is a Python `set` of such strings.

A **rule** is a pair: a tuple of conditions and a conclusion. The rule

```python
(("passed_programming1", "can_take_discrete"), "can_take_algorithms")
```

means “if `passed_programming1` and `can_take_discrete` are both known, then `can_take_algorithms` is known too”. A rule with a single condition still uses a tuple, which in Python needs a trailing comma: `("passed_math1",)`. A list of rules is a plain Python list, and “rule number $i$” means `rules[i]`.

<Step n={3} title="Part A: is an argument valid?" time="12 min" id="validity">

Your first two functions are the Python version of the argument checker on the week 6 page. An argument here is a list of premises and a conclusion, and each of them is a function of $n$ booleans. For example, the conditional $p \to q$ is written `lambda p, q: (not p) or q`.

**`counterexample(premises, conclusion, n)`** goes through every row of the truth table, using `product([True, False], repeat=n)` exactly as in Lab 1. In each row, it asks two questions: are **all** the premises true, and is the conclusion **false**? The first row where both answers are “yes” is a counterexample, and the function returns it. If no row qualifies, it returns `None`.

When you call a premise on a row, unpack the tuple with a star: `p(*row)`. To check that every premise is true in that row, `all(p(*row) for p in premises)` does the job.

**`is_valid(premises, conclusion, n)`** is then a single line: an argument is valid exactly when it has no counterexample.

```python
implies = lambda a, b: (not a) or b
counterexample([lambda p, q: implies(p, q), lambda p, q: q], lambda p, q: p, 2)
# (False, True): p is false, q is true, both premises hold, the conclusion fails
```

That is the fallacy of affirming the conclusion, caught by your own code.

</Step>

<Step n={4} title="Part B: can a rule fire?" time="5 min" id="can-fire">

**`can_fire(rule, facts)`** decides whether a rule is ready to produce something new. Two things must be true at the same time: **every** condition of the rule is already a known fact, and the conclusion is **not** yet known. The second requirement matters more than it seems: without it, the engine would “discover” the same fact again and again and never stop.

```python
can_fire((("a", "b"), "c"), {"a", "b"})   # True
can_fire((("a", "b"), "c"), {"a"})        # False: b is not known yet
can_fire((("a",), "c"), {"a", "c"})       # False: c is already known
```

A natural way to write it is to unpack the rule first, `conditions, conclusion = rule`, and then combine `all(...)` with a membership test.

</Step>

<Step n={5} title="Part B: forward chaining" time="12 min" id="forward">

**`forward_chain(facts, rules)`** is the engine from the notes. It returns the set of **all** facts that follow from the starting facts.

Here is the plan, in words. Start from a **copy** of the facts, never the original set: `known = set(facts)`. Then make passes over the rules. During a pass, go through the rules in order, and whenever a rule can fire, add its conclusion to `known`. Keep a flag that remembers whether this pass added anything. When a complete pass adds nothing new, stop and return `known`.

```python
forward_chain({"a"}, [(("a",), "b"), (("b",), "c")])    # {"a", "b", "c"}
```

> [!warning] One pass is not enough
> It is tempting to loop over the rules once. The checks include a case where the rules are listed in the “wrong” order, so that each rule only becomes ready after the next one has fired. Only an engine that keeps making passes until nothing changes will find every fact. If you are unsure, look again at the forward-chaining section of the week 6 notes, which explains exactly this.

</Step>

<Step n={6} title="Part C: remembering why" time="10 min" id="reasons">

A rule engine that cannot explain itself is hard to trust. The first step towards explanations is to remember **which rule** produced each fact.

**`reasons(facts, rules)`** runs exactly the same passes as `forward_chain`, but instead of a set it builds a dictionary. Every starting fact maps to `None`, and every derived fact maps to the **number** of the rule that first added it.

```python
reasons({"a"}, [(("a",), "b"), (("b",), "c")])    # {"a": None, "b": 0, "c": 1}
```

Two small tips. Use `for i, rule in enumerate(rules)` to get the rule numbers. And you can reuse `can_fire(rule, why)` with the dictionary itself, because the `in` test on a dictionary checks its keys.

</Step>

<Step n={7} title="Part C: explaining a conclusion" time="12 min" id="explain">

**`explain(goal, facts, rules)`** turns those reasons into a story: the list of facts needed to reach the goal, in an order in which each fact can be derived from the ones before it, ending with the goal itself. If the goal does not follow at all, it returns `None`.

The cleanest way to write it is with a small helper function inside `explain` that **visits** a fact:

- if the fact is already in the list, do nothing;
- if the fact was derived by rule $i$, first visit each condition of `rules[i]`, in the order they are written;
- then append the fact to the list.

Call the helper on the goal, and return the list.

```python
rules = [(("a",), "b"), (("b", "x"), "c"), (("a",), "x")]
explain("c", {"a"}, rules)     # ["a", "b", "x", "c"]
```

Read the result aloud and it becomes an argument in the style of the notes: we know `a`; from `a`, rule 0 gives `b`; from `a`, rule 2 gives `x`; from `b` and `x`, rule 1 gives `c`.

</Step>

<Step n={8} title="Part D: backward chaining" time="15 min" id="backward">

Forward chaining computes everything it can and only then looks at the question. **Backward chaining** starts from the question and only explores what it needs, which is how we planned the lake argument in the notes.

**`backward_chain(goal, facts, rules, visiting=None)`** answers “can `goal` be proved?” with three cases:

1. If the goal is a known fact, the answer is `True`.
2. If the goal is already in `visiting`, we are going round in a circle, so this branch fails: return `False`.
3. Otherwise, look at every rule whose conclusion is the goal. If **all** of that rule's conditions can be proved, by calling `backward_chain` on each of them, the goal is proved. If no rule works, return `False`.

This is your first **recursive** function in this course: it calls itself on smaller questions. When you make those calls, pass `visiting | {goal}` as the last argument, so that each branch remembers which goals it is already working on. At the very start, when `visiting` is `None`, replace it with an empty set.

```python
backward_chain("c", {"a"}, [(("a",), "b"), (("b",), "c")])    # True
backward_chain("x", {"a"}, [(("x",), "y"), (("y",), "x")])    # False: a circle that never reaches a fact
```

Without the `visiting` check, the second example would call itself forever until Python stops it with a `RecursionError`. The checks also compare your backward chaining with forward chaining on forty random rule bases: the two strategies must always agree.

</Step>

## Troubleshooting

> [!note] `TypeError: 'str' object is not callable` or strange results with one-condition rules
> A tuple with one element needs a comma: `("passed_math1",)`. Without the comma, `("passed_math1")` is just a string, and looping over it gives single letters.

> [!note] `forward_chain` passes the first check but not the “wrong order” check
> Your engine makes only one pass. Keep looping until a whole pass adds nothing new.

> [!note] “forward_chain must not modify the facts it receives”
> Start with `known = set(facts)` and add to `known`, not to `facts`.

> [!note] `RecursionError: maximum recursion depth exceeded`
> Your `backward_chain` is going round a circle of rules. Check the `visiting` set before trying the rules, and pass `visiting | {goal}` to every recursive call.
